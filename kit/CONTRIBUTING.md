# Contributing documentation

This repository holds Markdown only. Menus, section pages, "Related documents",
search and access are all generated by the shared portal kit
(`company-resources/kit/`). You never edit a menu or a config file to add a page.

## Two ways to contribute

**Not on GitHub (most employees).** Download `template.md` and `example.md` from
the portal front page, fill in the template, and email it to
**wikki@nerdience.com**. The docs team checks it and adds it here.

**Docs team (GitHub).** Add or edit the file yourself:

1. On GitHub, open `docs/`, go to the folder you want, then **Add file → Create
   new file**. To create a new folder, type it in the name box:
   `people/benefits/health-insurance.md` creates `benefits/` automatically.
2. Paste the content (it must start with the template's frontmatter block).
3. Choose **Create a new branch and start a pull request**, then open the PR.
4. Checks run (metadata, links, secrets, build). Another docs-team member
   reviews and merges. The site updates after the deploy finishes.

## What happens automatically

| You do | The build does |
| --- | --- |
| add a page to a folder | menu entry, card on the section page, search entry, "Related documents" links |
| create a new folder | new menu section with its own section page (an `index.md` with a one-line description is optional) |
| add `order: 1`, `order: 2` … | menu and cards follow that order (otherwise A–Z) |
| move, rename or delete | menu updates; broken links fail the check |
| set `tags:` | pages sharing tags link to each other under "Related documents" |
| leave `last_reviewed` too old | page shows a red "Review overdue" badge |

## Who can see a page

A page belongs to the portal site whose folder matches it best in
`company-resources/kit/portals.yml`. A **new folder joins this repository's
main site automatically**. If a folder needs a smaller audience (for example
`management/` or `people/performance/`), a portal maintainer adds one entry to
`portals.yml`; that folder then becomes its own protected site, and its pages,
titles and search entries disappear from the main site.

The check refuses a page whose `classification` is not allowed in its site,
so a `restricted` page cannot end up in an all-employee site by mistake.

## Required metadata

`title`, `owner`, `department`, `classification` (public | internal |
restricted), `status` (draft | review | approved | review-due | deprecated),
`version`, `last_reviewed` (YYYY-MM-DD), `review_cycle_days`, `tags`.
An `approved` page also needs a real owner, `approved_by` and `approved_on`.

Never put passwords, tokens, salaries, bank details or personal data in a page.

## Build locally (docs team, optional)

With `company-resources` checked out next to this repository:

```bash
pip install -r ../company-resources/kit/requirements.txt
python ../company-resources/kit/scripts/validate.py
python ../company-resources/kit/scripts/build_all.py
python -m http.server 8000 --directory build/<site>/site
```
